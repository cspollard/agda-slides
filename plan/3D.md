# A 3D module: objects, views, and projection to `Dia`

Status: proposal. Prompted by `src/Slides/Examples/ATLAS.agda`.

## Verdict

Yes, but a small one, and not yet in the core.  `ATLAS.agda` (434 lines) has grown a private 3D
engine: a sine, a view, a projection, a visibility test, a painter's order, translucent faces.
Those parts are not about a detector; the next 3D picture (a cube for a tensor, a stack of
layers in a network, a calorimeter tower, a Feynman-diagram-in-space) would copy them.  Pulling
them out also makes the detector code shorter and the engine testable on its own.

What it should **not** be: a renderer.  Output stays a `Dia ℕ` built from `polygon`,
`polyline`, `disc` and `place`, so every backend, the layout laws and the animations keep
working, and nothing in `Slides.Diagram.*` changes.  3D is a front end that compiles to `Dia`,
the way `Convenience` does.

## What ATLAS has that is general

| In `ATLAS.agda` | General form |
|---|---|
| `sinQ`, `trig`, `sc` (table sine, 1/1024 turns) | `Slides.Trig`: `sin n`, `cos n`, a Taylor polynomial of user-chosen order `n` on a rational angle |
| `View yaw roll`, `proj` | `View`, `project : View → Point → ℤ × ℤ` |
| `(r , a , z)` points | cylindrical coordinates, converted to `Point` |
| `cell`, `patch`, `wall`, `arcPts` | `Shape3` primitives: prism, annular sector, disc, cylinder |
| `seen` (back-face test: normal's x times sin yaw) | `facing : View → Face → Bool` |
| layer list, topmost first | painter's order: `sort : View → List Face → List Face` |
| fill polygon (opacity) plus outline polygon | `Material` (fill, opacity, rim) and `render` |

What is detector-specific and stays in `ATLAS.agda`: the `Theme`, the layer table, the lit-cell
lists, the tracks, the legend.

## Design

### 1. Numbers: ℚ inside, ℕ at the edge

`Dia S` is parametric in its scalar (`Slides.Scalar.Space`; models `Model.Nat` and `Model.Rat`), and
layout needs only `Space S`.  The ℕ restriction is at the deck entry point (`diagram : String → ℕ →
Dia ℕ → Flow`) and the static printer (`natPrint`); the animation backend already prints `Layout ℚ`
(`qPrint`).  So the 3D module can build `Dia ℚ` directly, with no quantising step.  Open: whether a static
`Dia ℚ` can reach a slide today without going through `Anim` (check `Slides.Deck.Anim`, `rests`); if not,
the fix is a `ℚ` overload of `diagram`, a deck-level change, not a `Diagram` one.  Until that is
settled, `render` takes a `Quantise` argument: `id` for ℚ, or round-to-`ℕ` (with the frame offset,
clamped at 0) for `Dia ℕ`.  Rounding then happens once, at the last step.  ATLAS instead rounds in `ℤ` with 10⁸/10¹²
scalings and a +2000 offset after each stage; that bookkeeping and its accumulated error go away.

- Type: `Data.Rational.Unnormalised` (`ℚᵘ`) inside the pipeline: no gcd per operation, and
  we only compare at the end.  `Model.Rat` is on normalised `ℚ`, so the last step normalises
  (`ℚᵘ.↥`/`↧` to `ℚ`) when building `Dia ℚ`.
- Denominators grow under composition (yaw, then roll, then pitch, then a Horner polynomial).
  The module offers `snap : ℕ → ℚᵘ → ℚᵘ` (round to a denominator `D`) and a `Precision`
  parameter saying where to apply it (per vertex after `rotate`, by default).  Everything is
  computed per vertex and per distinct angle, never per pixel, so the cost is small.
- No `Float`, so output is reproducible and `--safe` holds.

**Angles and trig, no tables.**  `Slides.Trig` is parametrised by an order `n`:

```
sin cos : (n : ℕ) → Angle → ℚᵘ        -- Angle is a rational number of turns
```

1. Reduce to the first octant by exact symmetries (`sin (t + ½) = - sin t`, `sin (¼ - t) = cos t`,
   and so on).  This is exact in ℚ, so it needs no approximation and is where the provable
   laws live.
2. Evaluate the Taylor polynomial of order `n` by Horner's rule on the reduced angle.  On
   |x| ≤ π/4 the error is at most (π/4)^(n+1)/(n+1)!, which falls quickly: n = 5 gives about
   3·10⁻⁴ and n = 9 about 10⁻⁸, plenty for pixels.  `π` enters only through a rational
   approximation `piQ`, itself a parameter (a convergent such as 355/113, or a longer one).
   A minimax polynomial of the same order is a drop-in replacement for the coefficients table
   later (smaller error, same shape); the interface does not change.
3. `View` takes its default order from a `Precision` record, so a user picks the cost/accuracy
   trade once.

**Views need no trig at all, if we want.**  A rotation by a rational `t = tan (θ/2)` has
`cos = (1 - t²)/(1 + t²)`, `sin = 2t/(1 + t²)`, exactly, so the rotation matrix is exactly
orthogonal and rotations compose with no approximation.  Offer `viewT : ℚ → ℚ → View` next to the
angle-based `view`.  Trig is then only needed for placing things at an angle (cell starts,
arcs), where an error of 10⁻⁴ is invisible.

Accuracy is **not** proved (the library has no reals).  What is proved: odd/even symmetry and
the reduction identities (exact in ℚ), `sin 0 = 0`, `cos 0 = 1`.  Accuracy is checked by closed
tests: `sin n` against a few exact values and a bound, decided on ℚ.  Keep these off the
typechecking path of normal modules (a `refl` on ℚ normalises slowly); put them in a separate
`Three.Check` module.

- `Slides.Three.Point`: `record P3 : Set where x y z : ℚᵘ`; `cyl : ℚᵘ → Angle → ℚᵘ → P3` for the
  `(r , a , z)` ATLAS uses, `y` down the page, `z` toward the viewer.

### 2. Views

```
record View : Set where
  yaw roll : ℕ            -- about the vertical axis, about the line of sight
  -- later: pitch, perspective : Maybe ℕ
rotate  : View → P3 → P3   -- the two rotations, in the order ATLAS uses
project : View → P3 → ℤ × ℤ -- orthographic: drop z
```

The scaling bookkeeping (10⁸, 10¹², the +2000 rounding offset in ATLAS) is the fragile part and
should live here once, with a lemma that `flat` is the identity on `(x , y)`.  Pitch is the
missing rotation and the one a 3D module should offer, because the third axis is the point of a
general module; ATLAS only needs two.  Perspective is a later option (division by `d - z`);
orthographic is enough to start and keeps everything in `ℤ` without division per vertex.

### 3. Objects

```
data Face : Set where
  face : List P3 → Face            -- a planar convex polygon, vertices in order

record Material : Set where
  fill : String ; opacity : ℕ ; rim : String ; rimWidth : ℕ

record Solid : Set where
  faces    : List Face
  material : Material

Scene = List Solid
```

Primitives, each returning a `Solid`, each a few lines on top of `cyl`:

- `box`, `prism : List P2 → ℤ → Solid` (extrude a base polygon along z)
- `annularSector r₀ r₁ a w z₀ z₁`: ATLAS's `cell`/`patch`/`wall` combined: this is the one
  every calorimeter cell is
- `cylinder`, `tube` (a ring of `annularSector`s), `disc`
- `polyline3 : List P3 → Style → Scene`, a line rather than a solid, for tracks

### 4. Rendering

```
render : View → Scene → Dia ℕ
```

1. rotate all vertices once;
2. drop faces that fail `facing` when the solid is closed (ATLAS's `seen`) — an option on the
   `Solid`, since an x-ray overlay such as the tracks wants all faces;
3. order faces back to front by mean depth (painter's algorithm);
4. each face becomes a fill `polygon` (opacity, no stroke) plus an outline `polygon`, exactly
   the translucent-with-opaque-rim trick ATLAS uses;
5. `layers` them, topmost first.

Painter's algorithm by mean depth is wrong for interpenetrating or large non-convex faces.  That
is acceptable for the cases that motivate this (concentric shells, boxes, cells) and is also what
ATLAS does now by hand.  Document the limitation and the escape hatch (the caller can pass an
explicit order: `renderOrdered`, which is what ATLAS's staircase cut effectively does).  Do
**not** attempt hidden-line removal or BSP in the first version.

### 5. Placement in the tree

```
src/Slides/Trig.agda            table sine, quadrant lemmas
src/Slides/Three/Point.agda     P3, cyl
src/Slides/Three/View.agda      View, rotate, project, flat/turned
src/Slides/Three/Solid.agda     Face, Material, Solid, primitives
src/Slides/Three/Render.agda    facing, depth order, render
src/Slides/Three.agda           re-exports
```

Outside `Diagram`, depending on `Diagram.Convenience`.  It must not be imported by the core
(`docs/Map.md`'s check-core stays untouched).

## Refactoring ATLAS

After the module exists, `ATLAS.agda` loses `sinQ`..`proj`, `cell`/`patch`/`wall`/`arcPts`, `seen`
and the polygon/outline pairs: roughly 150 of its 434 lines, leaving the theme, layer table,
events, and legend.  Acceptance: do the move first with the *existing* table and `ℤ` arithmetic, and require the four
SVGs (`atlas`, `atlasTurned`, each dark and light) to be byte-identical before and after.  Only
then swap the numeric core for ℚ and polynomial trig as a separate commit; that one changes
rounding, so accept a reviewed diff (every vertex within one pixel of before, same layer order).

## Order of work

1. Move the code out of ATLAS unchanged: `Point`, `View`, `project` with the existing table and
   `ℤ` scalings.  Byte-identical SVGs.
2. Move the table to `Slides.Trig` (LHC imports it).  Byte-identical.
3. Swap to ℚᵘ and polynomial `sin`/`cos` of order `n` (and `viewT`).  Delete the table.  Reviewed
   diff, at most one pixel per vertex.  Compare `n` = 5, 7, 9 and keep the smallest that is
   not visibly different.
4. `Solid`, `annularSector`, `render`; ATLAS's `cell`, `lit`, `rear`, `front` use them.
5. Add `pitch`, `box`, `cylinder`, and one new example that is not a detector (a cube with
   labelled faces for a tensor slide).  If it needs something the first did not, that is the
   design feedback this step exists for.
6. Optionally: perspective, an `Anim` hook (a `View` is a few numbers, so a rotation over a slide
   sequence is a natural `Anim` parameter), and a reveal of solids one by one.

## Open questions

- **Depth ordering API.**  Per face, per solid, or caller-supplied?  ATLAS needs per-solid for
  shells and per-face inside a cell.  Proposal: sort faces within a `Solid` by depth; order the
  solids as given.  Revisit after step 4.
- **Where the sine lives.**  `Slides.Trig` under `Slides` (shared), not under `Three`: an arc in
  `Diagram` or a pie chart wants angles too.
- **Precision.**  Settled by the order parameter and `snap`, not by an angle unit.  `Angle` is
  still a one-field record (rational turns) so the representation can change.
- **ℚ in the core?**  Not now.  `Dia` stays `ℕ`; only this module quantises.  If a second front
  end (plots, graphs) also wants rationals, revisit a `Dia` over a coordinate type, as its own
  plan, since it touches the laws.
- **Proofs.**  Project principle is to prove laws.  Worth it here: `flat` is the identity,
  `project` is invariant under adding full turns, `rotate` by 0 is the identity.  Not worth it:
  geometric correctness of the painter's order.  Decide whether these go in a `Three.Laws`.
- **Is it worth it without a second user?**  Step 5 is the answer: if no second picture is
  wanted soon, stop after step 3 (numbers, trig and views), which already removes the fragile part from
  ATLAS at little cost, and defer solids and rendering.
